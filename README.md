## Решения

Подробные объяснения — в docstring модулей, здесь только главное.

**Факториал.** `reduce(operator.mul, range(2, n + 1), 1)`. Начальное значение 1 — это
произведение пустого набора чисел, поэтому 0! и 1! получаются без отдельной ветки.
Без начального значения `reduce` на пустом диапазоне бросил бы `TypeError`.

**Генератор простых.** Бесконечный: сколько чисел взять, решает вызывающий код
(`islice`, `takewhile`). Алгоритм — решето Эратосфена без верхней границы: для
каждого простого p хранится только его ближайшее непройденное кратное, а вычёркивание
начинается с p². Поэтому в памяти только простые до √n. Простые для вычёркивания даёт
отстающий экземпляр той же реализации; он заводит свой, но глубина цепочки растёт как
log log n: для первых 100 000 простых работают четыре решета. Само решето вынесено в
класс `_Sieve` — оно общее у генератора и класса-итератора.

**Несколько функций через `map`.** Формулировка допускает четыре трактовки:
группировка по элементам (кортеж на элемент), группировка по функциям (список на
функцию), «каждая функция ко всему списку целиком» (`sum`, `max`, `len`) и «функции по
цепочке» — последнее это конвейер из повышенного задания №9. Выбрана группировка по
элементам: поэлементный обход и есть `map`, а результат остаётся ленивым и работает на
одноразовых и бесконечных потоках. Группировка по функциям получается из неё одним
`zip`, обратно — нет: каждой функции пришлось бы читать поток заново.

**Класс-итератор.** `PrimeIterator` — тот же алгоритм, что у генератора, записанный
через `__iter__`/`__next__`. Решето у обоих буквально одно и то же (`_Sieve`), поэтому
сравнение показывает ровно то, ради чего задание и дано: что делает `yield`. Генератор
сам помнит локальные переменные и место остановки, а класс хранит это в атрибутах
`_emitted` и `_last` и по ним понимает, откуда продолжить. Отстающий источник простых
создаётся при первой надобности, а не в `__init__` — иначе каждое решето создавало
бы следующее, и конструктор упал бы с `RecursionError`; генератору эта ленивость
достаётся даром. Поверхностное копирование запрещено: копия делила бы состояние
решета и выдавала бы составные числа (генераторы по той же причине не копируются).

**Конвейер.** Шаг — функция «поток → поток», `pipeline(*steps)` соединяет шаги через
`reduce` и возвращает новую функцию. Готовые шаги `keep`, `transform`, `take` —
обёртки над `filter`, `map`, `islice`, поэтому промежуточных списков нет: каждый
элемент проходит все шаги до того, как взят следующий. Шаги проверяются при сборке,
результат шага — при запуске; в обоих сообщениях есть номер шага. Конвейер сам
является шагом и может входить в другой конвейер.

**Проверка аргументов** одна на весь пакет ([`checks.py`](funclab/checks.py)): не тот
тип — `TypeError`, недопустимое значение — `ValueError`, `bool` числом не считается,
сообщение начинается с имени аргумента («n: …», «функция 2: …», «шаг 3: …»). Поэтому
и `take(10**100)` отвергается при сборке конвейера, а не падает при запуске английским
сообщением из `islice`.

## Ограничения

- `factorial` перемножает числа по одному, а `math.factorial` — попарно, поэтому на
  больших n он заметно быстрее; конкретный разрыв зависит от машины и версии Python.
- `primes()` и `PrimeIterator` бесконечны и `StopIteration` не бросают; без
  `islice`/`takewhile` цикл по ним не закончится.
- Шаг конвейера, которому нужен весь поток (например, `sorted`), читает его сразу
  при запуске и на бесконечном входе не завершится.
- Ошибка внутри функции пользователя в `map_all` или конвейере появляется не при
  вызове, а когда очередь доходит до этого элемента: вычисления ленивые. Номера шага
  в таком сообщении нет — оно приходит от самой функции.
- Ленивы именно вычисления, а не проверка аргументов: `map_all` берёт итератор по
  элементам сразу при вызове, поэтому негодный аргумент отвергается там же, а не при
  первом `next`. Встроенный `map` ведёт себя так же.
